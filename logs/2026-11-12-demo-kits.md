# 2026-11-12: Demo kits

- Changes: implemented [the demo-kit spec](../workflow/specs/2026-11-12-demo-kits.md),
  modelled on the MP3 Homebrew team's public kit button but limited to two
  logins.
  - **Sign-in page:** **Create demo kit** creates a verified PM and a verified
    Developer with random `@example.com` emails and passwords, shown once. It
    creates no organisation or requests.
  - **Limits:** a 10-minute limit and a daily limit, each with its own
    persistent notice that says when to retry and links to sign-up. An outage
    shows a separate red message.
  - **Database rules:** a service-role-only reservation RPC with an advisory
    lock, 5 kits per 10 minutes and 30 per Singapore day. A deferred constraint
    trigger reserves `demo_` usernames for marked accounts. The marker is
    `app_metadata.demo_kit`, which Auth writes after inserting the user, so the
    check runs at commit.
  - **Removal:** `npm run demo:remove` is a dry run by default and needs a
    matching `--project`. It selects only by the exact marker and prints counts
    only.
  - The guides and the Acceptance Index are updated.
- Validation:
  - `npm run verify` passed (247 tests).
  - `npm run test:integration`: 89 passed, including 10 demo-kit database and
    removal tests (grants, 12-way concurrency, daily limit, trigger spoofs,
    decoys, batching).
  - The full browser suite passed (56), including a no-mailbox kit journey and
    the daily notice.
  - Checked visually on desktop and at 375px.
- Review: the security preflight added 13 requirements, all met. The code review
  found three blocking issues, all fixed:
  - the remove command put every account id into one URL, so its lookups are
    now batched;
  - a stray generated `next-env.d.ts` change was reverted;
  - this log was missing.
  It also suggested smaller fixes, all made: an unneeded grant dropped, the
  live region kept mounted, and tests added for the pending state and for a
  reply that arrives after leaving the page.
- Security review (after the change): approved. Three low or informational
  notes are recorded in the Developer Guide:
  - the removal warning does not count what demo accounts wrote in other
    people's organisations;
  - out-of-range caps are rejected rather than clamped;
  - a timed-out request can leave a marked orphan account for `demo:remove`.
- Open:
  - The deferred-trigger design relies on Auth writing `app_metadata` in the
    same transaction as the user insert. This was verified only on the local
    Auth version. Create one kit on development after the first Render deploy,
    and run a `demo:remove` dry run there.
  - Acceptance criterion 1 is not checked on a hosted environment. That needs
    the first Render deploy. Locally, the journey stops at accepting the
    invitation.
  - The notices state the default caps, 5 and 30, even if an environment sets
    lower ones.
