# Demo kits

Status: approved by the user on 2026-11-12 ("Approve as drafted"), including
distinct burst and daily limit notices. Replaces the earlier demo-kit
outline in the [product MVP](2026-11-07-product-mvp.md): a kit is now two
logins only, with no organisation or sample requests.

## Problem and user

Peer testers need to try both roles on a deployed SpecForge without giving a
personal email address or opening a mailbox. Following the MP3 Homebrew team's
approach, anyone on the sign-in page can create a kit. They see a verified PM
login and a verified Developer login once, then use the product exactly like
ordinary users. They create an organisation, invite the other account by its
email and continue from there.

## Behaviour

- The sign-in page has a **Try SpecForge** section below the form. Its
  **Create demo kit** button creates one kit in the environment serving the
  page. Development and production both offer it.
- A kit is two Supabase Auth accounts created by the server with confirmed
  email:
  - **PM:** email `demo-pm-<code>@example.com`, username `demo_pm_<first 8 of code>`.
  - **Developer:** email `demo-dev-<code>@example.com`, username `demo_dev_<first 8 of code>`.
  - `<code>` is 32 random lowercase hex characters. Each password is 24 random
    bytes encoded as base64url. Both come from the server's cryptographic
    random source.
  - The server-only Auth `app_metadata` records `demo_kit: <code>`. This is the
    only marker that identifies a demo account. Emails and usernames do not.
- No organisation, membership, invitation, request or other row is created.
  The existing profile trigger creates each profile from the role and username.
- The page shows both logins (role, email, password, each with a copy button).
  It says they are shown once and cannot be recovered, and that the sign-in form
  above is where to use them. The credentials are cleared on `pagehide` and on
  unmount, so a page restored from browser history never shows them again.
- Demo accounts behave identically to ordinary accounts: the same role
  permissions, AI quotas, profile editing (including renaming) and sign-out.
- Kits stay until a maintainer removes them. Nothing expires them automatically.
- The **User Guide** explains how to try SpecForge with a demo kit. The
  **Developer Guide** documents the endpoint, the caps and the remove command.
  The User Guide's "Demo kits remain future work" line is removed.

## Admission and failures

- `POST /api/demo-kits` takes an empty JSON object, has no session, and passes
  the app's existing same-origin check. Any other method returns 405. A
  non-empty or invalid body returns 400. Responses carry the existing
  `private, no-store` headers.
- A site-wide creation cap is stored in the database per environment, with no
  per-IP or per-process state: at most **5 kits per 10 minutes** and **30 per
  Singapore calendar day**. A transaction-locked server-only RPC reserves one
  slot against both windows before any account is created. A reserved slot is not
  refunded if creation fails.
- A full window returns 429 with `Retry-After` and a `limit` of `burst` or
  `daily`. The page shows a persistent, non-error notice (not the red failure
  style) that names the limit as deliberate, says when to retry, and offers the
  normal route:
  - **Burst:** "Demo kits are limited to 5 every 10 minutes to protect the
    service. Try again in N minutes, or create an account with your own email."
  - **Daily:** "Today's 30 demo kits have all been used. New kits are available
    from midnight Singapore time (in about N hours). You can still create an
    account with your own email."
  - The waiting time is rounded up to whole minutes for the burst limit and to
    whole hours for the daily limit, never shown as 0. "create an account" links
    to `/sign-up`.
  - While the notice is shown, **Create demo kit** stays enabled. Pressing it
    again re-checks and refreshes the notice.
- A 503 keeps its separate red "temporarily unavailable" message, so a limit
  is never mistaken for an outage, and an outage never for a limit.
- Caps are server configuration (`DEMO_KITS_PER_10_MINUTES`,
  `DEMO_KITS_PER_DAY`). They default to 5 and 30. Values above those numbers,
  and any value that isn't a whole number, are rejected and the endpoint answers
  503. A cap of 0 turns the feature off.
- Creation is all-or-nothing from the tester's view. If the second account fails,
  the server deletes the first (one bounded retry). The response is 503 "Demo
  kit service is temporarily unavailable. Try again." and returns no
  credentials. An account whose creation acknowledgement was lost holds a
  `demo_kit` marker and is cleaned up by the remove command.
- Missing `SUPABASE_SECRET_KEY` or a database failure returns the same 503.
  Failures go through the existing allowlisted server-failure log. Emails,
  passwords and kit codes are never logged, stored in application tables or
  returned on error.
- The public sign-up and the profile rename both reject any new username
  starting with `demo_` with the existing "Choose a different username." This is
  enforced in the API and in the database (`private.create_profile`,
  `public.rename_username`), so a `demo_` name always came from a kit. The
  trigger accepts the prefix only when `raw_app_meta_data` carries `demo_kit`,
  which only the secret-key Admin API can set. Existing usernames are not
  touched.
- No LLM, SoC call or prompt is involved.

## Removal

- `npm run demo:remove` runs from a maintainer machine. It takes the target
  environment's `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SECRET_KEY` from the
  environment.
  - It selects users by `app_metadata.demo_kit` only, using the paginated Admin
    API, with either `--kit <code>` or `--all`.
  - By default it is a dry run: it prints the number of kits and accounts found,
    and the number of organisations those accounts created.
  - `--yes` deletes the accounts. Deleting a profile already cascades: it
    deletes organisations the account created, with their tickets, and the
    account's memberships and private data. The dry run says so.
  - It prints counts only. It never prints emails, passwords, the secret key or
    the Supabase URL.

## Acceptance criteria

1. On development and production, an anonymous visitor creates a kit and signs
   in with each login without opening any mailbox. The PM can create an
   organisation, invite the Developer's email and draft a ticket. The Developer
   can accept the invitation and open the published ticket.
2. Each kit yields exactly two verified accounts with distinct random emails,
   usernames and passwords. No organisation or request rows are created.
3. The sixth kit inside one 10-minute window, or the 31st in one Singapore day,
   gets 429 with `Retry-After` and creates no account. This holds across server
   instances and restarts. The page shows the matching burst or daily notice,
   with a sensible waiting time and the sign-up link, and not the outage message.
4. A failed second account leaves no account from that kit and returns 503
   without credentials.
5. A public sign-up or rename to `demo_x` fails in the API and directly in the
   database. A kit's `demo_` names succeed.
6. Credentials are not shown again after reloading the page or navigating back.
7. `demo:remove` dry runs change nothing. `--yes` removes only marked accounts
   and leaves ordinary accounts with similar emails or names untouched.
8. Server logs from every path above contain no email, password or kit code.

## Security

Classed as sensitive: unauthenticated account creation through the secret key,
a public trust boundary, and a deletion tool. It needs a security preflight
before coding and a security review after. Residual risks to accept explicitly:

- A shared global cap lets one visitor use up the day's kits.
- Demo accounts add AI quota. The worst case is 30 PM accounts × 20 requests
  per hour per environment.
- Testers may share kit credentials.

### Preflight requirements (2026-11-12)

The independent preflight added these requirements to the spec above:

- **Marker source.** The trigger reads the marker only from
  `raw_app_meta_data`, and only when it is a string matching `^[0-9a-f]{32}$`.
  It is never read from `raw_user_meta_data`, which users can write. The name
  must equal the role's `demo_pm_`/`demo_dev_` plus the code's first 8
  characters. The prefix is checked after lowercasing.
- **Database access.** The reservation table is in `private` with RLS on.
  `anon` and `authenticated` cannot reach the RPC or the table. The RPC takes
  its time from the database clock, rejects out-of-range caps, and serialises
  calls under an advisory transaction lock.
- **Order of operations.**
  - The reservation happens before any Admin call. A 429, a configuration error
    or a database error makes no `createUser` call.
  - The Admin client is never bound to cookies.
  - Accounts are created with `email_confirm: true` only, never through invites
    or links.
  - Compensation hard-deletes by the returned id.
- **Load shedding.** A separate per-process limit of 10 kit requests per minute
  sheds load first, before the database. Its 429 also carries `Retry-After` and
  `limit: "burst"`. The sign-in admission counter is not shared.
- **Logging.** Failures are logged with a stable `demo-kits` route label. Tests
  assert that no email, password or kit code reaches `console`.
- **Removal tool.**
  - It needs exactly one of `--kit` or `--all`.
  - It lists every page of users before any deletion.
  - It matches exact, string-typed `app_metadata.demo_kit` values, and re-reads
    each user to check the marker just before deleting.
  - It requires `--project <ref>` (or `local`) to match the target URL.
  - Its dry run also warns that ordinary members of demo-created organisations
    lose that membership.

## Testing interfaces

- **Unit (`src/tests/demo-kits.test.ts`):** the handler with fake admission and
  a fake Admin client. Covers method, origin and body rejection; 429 and 503
  mapping; credential shape; compensation on a failed second account; config
  validation; and the absence of secrets in failure logs.
- **Database (`src/tests/demo-kits.database.test.ts`, disposable local stack):**
  - reservation windows, concurrency and grants (`anon` and `authenticated`
    denied);
  - `demo_` reservation in the trigger and in the rename RPC;
  - an Admin-created kit producing exactly two profiles with no other rows;
  - remove-command selection by marker.
- **Component (`src/components/demo-kit.test.tsx`):** pending, success, the
  burst and daily notices (wording, rounding, sign-up link, never "0"), 503,
  copy buttons, clearing on `pagehide`, and accessibility checks.
- **Browser (`src/tests/browser/demo-kits.spec.ts`):** create a kit, sign in as
  each role, then the PM-invites-Developer journey. These check local
  integration. Hosted checks are recorded separately after a deploy.

## Exclusions

- Sample organisations, requests or test plans.
- Automatic expiry or scheduled cleanup.
- Restrictions specific to demo accounts.
- Per-IP limits, a CAPTCHA, or an admin UI for kits.
- Password recovery for lost kit credentials.
- Converting a demo account into an ordinary account.
